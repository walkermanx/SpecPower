# Phase 0 快速验证 vs Phase 1 完整探索

## 核心区别总览

| 维度 | Phase 0: 快速验证 | Phase 1: 完整探索 |
|------|------------------|------------------|
| **目标** | 确定使用哪个模式 | 理解全局上下文，为规范和设计奠定基础 |
| **时机** | 模式确定**之前** | Strict 模式确定**之后** |
| **时长** | ~30 秒 | 5-15 分钟（甚至更长） |
| **深度** | 表面扫描 | 深入分析 |
| **适用** | 所有任务（边界情况触发） | 仅 Strict 模式 |
| **产出** | 模式推荐 + 调整理由 | 上下文报告（内嵌于 proposal） |
| **可选性** | 高置信度时跳过 | Strict 模式必需 |

---

## 详细对比

### 1. 目标与定位

**Phase 0: 快速验证**
- 🎯 **回答问题**："这个任务应该用 Flow、Standard 还是 Strict？"
- 🎯 **核心价值**：避免模式选择错误
  - 防止用 Flow 做复杂任务（导致质量风险）
  - 防止用 Strict 做简单任务（导致效率浪费）
- 🎯 **比喻**：选工具（"用扳手还是螺丝刀？"）

**Phase 1: 完整探索**
- 🎯 **回答问题**："这个系统怎么工作？我的变更会影响什么？"
- 🎯 **核心价值**：充分理解上下文，确保规范和设计不脱离实际
- 🎯 **比喻**：用好工具（"螺丝刀已经选好了，现在要找准螺丝位置"）

---

### 2. 扫描范围

**Phase 0: 快速验证（3 个维度）**

```bash
# 第 1 步：影响范围（10秒）
glob "src/auth/**/*"           # 数文件数量
glob "**/*login*"              # 找相关文件

# 第 2 步：耦合度（10秒）
grep "login\(" --count         # 数引用次数
grep "class.*Auth" --count     # 找关键类型

# 第 3 步：测试覆盖（10秒）
glob "**/*auth*.test.*"        # 是否有测试
```

✅ **只关心**：文件数量、引用次数、有无测试  
❌ **不关心**：具体实现逻辑、架构模式、技术细节

---

**Phase 1: 完整探索（8+ 个维度）**

```bash
# 1. 项目上下文扫描（2-3分钟）
tree -L 2                              # 项目结构
cat package.json                       # 技术栈
cat tsconfig.json                      # 配置约定
ls -la **/*.test.*                     # 测试框架

# 2. 现有模式理解（3-5分钟）
read src/auth/**/*.ts                  # 读现有实现
grep "class.*Service"                  # 服务层模式
grep "interface.*Repository"           # 数据访问模式
read docs/architecture.md              # 架构文档

# 3. 影响范围确定（2-3分钟）
grep "import.*auth" -r src/            # 谁在用 auth
grep "authService\." -r                # 具体调用点
read src/api/routes.ts                 # API 路由影响

# 4. 约束发现（2-3分钟）
grep "performance" -r docs/            # 性能要求
git log --oneline -- src/auth | head  # 历史变更
read .env.example                      # 环境配置
```

✅ **深入理解**：架构模式、技术选型、现有实现、历史演进、约束条件  
✅ **读代码**：实际打开文件阅读实现细节  
✅ **看文档**：查找注释、README、架构文档

---

### 3. 信息深度

**Phase 0: 快速验证**
- 📊 **数量级判断**："这个模块有 12 个文件"
- 📊 **有无判断**："有测试覆盖" / "没有测试"
- 📊 **耦合判断**："被引用 15 次" / "只在一处使用"
- ❌ **不关心具体是什么**：不读代码内容

**Phase 1: 完整探索**
- 📖 **质量判断**："这个模块采用 Repository 模式"
- 📖 **历史追溯**："去年重构过一次，从 Express 迁移到 Fastify"
- 📖 **约束理解**："性能要求 P95 < 100ms，有 SLA 合约"
- 📖 **风险识别**："这个模块没测试，且是支付关键路径"
- ✅ **深入阅读**：打开代码文件，理解实现逻辑

### 4. 工具使用

**Phase 0: 快速验证**

```bash
# 只用 Glob 和 Grep（不带上下文）
glob "src/auth/**/*"                    # 找文件
grep "login" --count                    # 数引用
glob "**/*.test.*" | grep auth          # 找测试
```

特点：
- ✅ **快**：只看文件名、数数量
- ✅ **表面**：不打开文件看内容
- ✅ **过滤**：用 grep --count、glob 模式过滤

---

**Phase 1: 完整探索**

```bash
# 用 Read、Glob、Grep、Bash 组合
glob "src/auth/**/*"                    # 列文件
read src/auth/AuthService.ts            # 读代码
grep "import.*AuthService" -r -B2 -A2   # 看上下文
git log --oneline --stat -- src/auth   # 看历史
cat docs/auth-design.md                 # 读文档
```

特点：
- ✅ **慢但深**：打开文件阅读实现
- ✅ **上下文**：看前后几行代码
- ✅ **历史**：查看 git 历史、commit 信息
- ✅ **多源**：代码 + 文档 + 注释

---

### 5. 决策输出

**Phase 0: 快速验证**

输出格式：
```
初判：Standard
验证发现：涉及 12 个文件、跨 3 个模块、无测试
调整为：Strict
理由：复杂度高 + 技术债
```

特点：
- 🎯 **二元决策**：用哪个模式
- 🎯 **简短理由**：1-2 句话
- 🎯 **关注复杂度信号**：文件数、耦合度、测试

---

**Phase 1: 完整探索**

输出格式（内嵌于 proposal 的"上下文"部分）：
```markdown
## 上下文

### 现状
当前认证系统采用 JWT + Redis Session 混合方案。
核心模块：
- src/auth/AuthService.ts - 认证服务主入口
- src/auth/JwtProvider.ts - JWT 签发和验证
- src/auth/SessionStore.ts - Redis session 管理

依赖关系：
- API 层 20+ 路由使用 authMiddleware
- 前端 5 个模块调用 auth 接口
- 用户、权限、审计模块都依赖 auth

### 已知约束
- 性能：登录 P95 < 200ms（现状 180ms，接近红线）
- 兼容性：需保持现有 JWT payload 格式（移动端依赖）
- 安全：通过了去年 Q3 安全审计，不能降低安全等级

### 历史背景
- 2025-06 从 Session-only 迁移到 JWT+Session 混合
- 原因：支持移动端无状态认证
- 技术债：SessionStore 模块测试覆盖率为 0
```

特点：
- 📖 **详细报告**：几百字的上下文描述
- 📖 **多维度**：架构、依赖、约束、历史
- 📖 **为后续决策服务**：供 specs/design 阶段参考

## 关键要点

### Phase 0 的本质
- 🎯 **是什么**：模式选择器
- 🎯 **做什么**：快速判断任务复杂度
- 🎯 **不做什么**：不深入理解系统
- 🎯 **比喻**：医生的"初步诊断"（看症状、量体温）

### Phase 1 的本质
- 🎯 **是什么**：上下文收集器
- 🎯 **做什么**：深入理解系统现状和约束
- 🎯 **不做什么**：不决定用哪个模式（已确定）
- 🎯 **比喻**：医生的"详细检查"（拍片、化验、问诊）

### 为什么需要两个阶段？

**如果没有 Phase 0**：
- ❌ 问题：仅凭"改一下登录"就推荐模式 → 可能选错
- ❌ 浪费：选错模式后返工（Flow 做了一半发现应该 Strict）

**如果没有 Phase 1**：
- ❌ 问题：直接写规范/设计 → 脱离现实
- ❌ 风险：不了解约束和依赖 → 方案行不通

**两阶段配合**：
- ✅ Phase 0：用 30 秒避免选错模式
- ✅ Phase 1：用 10 分钟确保规范/设计贴合实际
- ✅ 分工明确：Phase 0 选工具，Phase 1 用好工具

## 常见误区

### ❌ 误区 1："Phase 0 也是探索，和 Phase 1 重复了"

正解：
- Phase 0 是**表面扫描**（数数量），Phase 1 是**深入理解**（读内容）
- Phase 0 回答"用什么模式"，Phase 1 回答"怎么做"
- Phase 0 对所有任务可选触发，Phase 1 只在 Strict 必需

### ❌ 误区 2："Phase 0 验证可以代替 Phase 1"

正解：
- Phase 0 只提供复杂度信号（多少文件、多少引用）
- Phase 1 提供实现细节（用什么架构、有什么约束）
- 两者信息粒度完全不同

### ❌ 误区 3："简单任务也要 Phase 0 验证"

正解：
- Phase 0 有跳过条件："修 typo"、"改配置" → 直接推荐 Flow，0 秒
- 只有**边界情况**才触发验证（"改一下登录"这种模糊的）
