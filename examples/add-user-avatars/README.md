# 示例：添加用户头像功能

这是一个完整的 SpecPower 端到端示例，展示如何使用 **Standard 模式**完成一个中等复杂度的功能开发。

## 场景描述

为用户系统添加头像上传和显示功能。用户可以上传 JPEG 或 PNG 格式的图片作为头像，系统会进行尺寸限制和格式验证。

## 模式选择

**推荐模式**: Standard 模式

**理由**:
- 涉及 3+ 文件（后端 API、数据库模型、前端组件、测试）
- 需要设计决策（存储方式、图片处理策略）
- 有一定复杂度但不涉及多模块重构

## 工件清单

本示例包含以下工件：

```
add-user-avatars/
├── .specpower.yaml          # 变更元数据
├── proposal.md              # 提案文档
├── specs/                   # 规范（Standard 模式可选）
│   └── users/
│       └── avatar-spec.md   # 头像功能规范（此示例包含以展示格式）
├── design.md                # 技术设计
└── tasks.md                 # 任务分解
```

**注意**: 本示例未包含实际的代码实现，因为代码会根据你的项目技术栈而不同。重点展示的是工件的格式和内容。

## 如何使用本示例

### 作为学习材料

1. **阅读顺序**: proposal.md → design.md → tasks.md
2. **理解工件间的关系**: 提案定义"做什么"，设计定义"怎么做"，任务定义"分步做"
3. **注意细节**: 每个工件的自审清单、决策理由、验证命令

### 作为模板

1. 复制整个目录: `cp -r examples/add-user-avatars docs/spec-power/changes/your-change`
2. 修改 `.specpower.yaml` 中的变更名称和日期
3. 替换内容为你的实际需求
4. 删除 `README.md`（这是示例说明文件）

### 使用初始化脚本

更推荐使用 `scripts/init-change.sh` 自动创建目录结构：

```bash
./scripts/init-change.sh my-new-feature standard
```

## 工件详解

### .specpower.yaml

变更的元数据，用于追踪状态和模式。

### proposal.md

回答三个核心问题：
- **为什么**要做这个变更？（动机）
- **做什么**和**不做什么**？（范围）
- **影响什么**？（兼容性、性能、依赖）

### design.md

记录技术决策：
- 至少考虑 2 个方案
- 说明为什么选择当前方案
- 关键接口定义
- 风险和缓解措施

### tasks.md

可执行的任务列表：
- 每个任务 2-5 分钟完成
- 文件映射精确（Create/Modify/Test）
- 标注依赖关系
- 每步包含验证命令

## 学习要点

### 1. 提案写作技巧

- ✅ 动机清晰：不了解项目的人也能理解
- ✅ 范围明确：说了"不做什么"
- ✅ 无占位符：没有 "TBD"、"待定"
- ✅ 影响分析：考虑了向后兼容性

### 2. 设计文档最佳实践

- ✅ 多方案对比：展示了思考过程
- ✅ 决策有理由：不是"更好"而是"因为 X 所以 Y"
- ✅ 接口精确：参数和返回值都明确
- ✅ 风险识别：至少列出一个风险

### 3. 任务分解原则

- ✅ 粒度合理：每个任务独立可验证
- ✅ 依赖清晰：可并行的任务已标注
- ✅ TDD 驱动：每个任务都从测试开始
- ✅ 验证命令：不只是"编写测试"，还要"运行测试确认失败"

## 常见问题

### Q: 为什么示例没有实际代码？

A: 因为代码实现高度依赖于项目的技术栈。一个 Node.js 项目和一个 Python 项目的实现完全不同。本示例聚焦于**工件格式和思维过程**，这些是跨语言通用的。

### Q: Standard 模式一定要写 specs 吗？

A: 不一定。specs 是 Strict 模式的必需工件。本示例包含 specs 只是为了展示格式。Standard 模式通常直接从 proposal 到 design。

### Q: 实际项目中的工件会更复杂吗？

A: 可能更简单也可能更复杂。这个示例是"中等复杂度"的参考。实际项目中：
- Flow 模式：可能只有一段话的提案
- Standard 模式：与本示例类似或稍简单
- Strict 模式：会有更详细的规范和更严格的审查

### Q: 如何判断我的任务适合哪个模式？

A: 参考 SKILL.md 的"模式选择"章节：
- Flow: ≤ 2 文件，需求明确
- Standard: 3+ 文件，需要设计决策
- Strict: 多模块，关键系统，需要长期维护
