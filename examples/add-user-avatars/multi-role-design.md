# 多角色方案对比示例（Strict 模式）

此文件展示头像功能在 Strict 模式下的三角色方案对比过程。实际使用中这些内容由子agent并行产出，最终选定方案展开为 `design.md`。

---

## 共享上下文

### 现状

当前用户系统的数据模型：

```typescript
interface User {
  id: string;
  username: string;
  email: string;
  created_at: Date;
  updated_at: Date;
}
```

前端在显示用户信息时，只能显示用户名首字母或占位符图标。

### 目标

- 用户可以上传和显示个人头像
- 系统能够高效存储和分发头像
- 为未上传头像的用户提供合理的默认展示

### 非目标

- 不提供图片编辑功能
- 不支持动图（GIF）

### 硬约束

- 技术栈: Node.js + TypeScript + PostgreSQL
- 兼容性: 不破坏现有 User API 的响应格式
- 性能底线: 头像加载 P95 < 500ms

---

## 架构师方案: 分层存储抽象

### 核心策略

引入 Storage Abstraction Layer（存储抽象层），将文件存储从业务逻辑中完全解耦。定义 `StorageProvider` 接口，对象存储（S3/OSS）作为默认实现，但本地文件系统、数据库等都可以作为可替换的后端。

图片处理作为独立的 `ImagePipeline` 模块，通过配置定义处理流水线（缩放、格式转换、水印），与存储层和业务层都解耦。

### 关键设计决策

1. **StorageProvider 接口抽象**: 选择定义统一存储接口而非直接调用 S3 SDK，因为这允许未来切换存储后端（测试用内存实现、开发用本地文件、生产用 S3）而不修改业务代码。
2. **ImagePipeline 独立模块**: 选择将图片处理逻辑独立为模块而非嵌入上传流程，因为图片处理规则（尺寸、格式、质量）可能独立于上传逻辑变化。
3. **事件驱动的缩略图生成**: 选择上传后发事件异步生成缩略图，而非同步阻塞上传请求，因为解耦了上传和处理的生命周期。

### 架构概要

```
Controller → AvatarService → StorageProvider (interface)
                           → ImagePipeline (interface)
                                ↓
                           S3StorageProvider (实现)
                           SharpImagePipeline (实现)
```

模块职责：
- `AvatarService`: 业务编排（验证→处理→存储→更新DB）
- `StorageProvider`: 存储读写抽象
- `ImagePipeline`: 图片处理抽象

### 优势

- 存储后端可替换，测试时用内存实现，不需要 mock
- 图片处理规则可独立变更（加水印、改尺寸），不动业务逻辑
- 模块职责清晰，新成员容易理解系统结构

### 已知代价与风险

- 引入了 2 个抽象接口 + 实现类，代码量比直接调用 S3 SDK 多约 40%
- 事件驱动缩略图增加了系统复杂度（需要考虑失败重试、最终一致性）
- 目前只有一种存储后端（S3），抽象在短期内是"过度设计"

### 与其他视角的预期分歧

- 性能专家可能认为: 事件驱动异步处理增加了端到端延迟，用户上传后不能立刻看到所有尺寸的缩略图
- 资深开发可能认为: 目前只需要 S3 一种后端，StorageProvider 抽象是 YAGNI（不需要的功能不要做）

## 性能专家方案: 同步流水线 + CDN 直推

### 核心策略

优先保证用户可感知的性能体验。上传时同步完成所有图片处理（验证、缩放、格式优化），直接推送到 CDN 存储，避免异步处理的一致性问题。重点优化热路径：头像加载走 CDN，永远不经过应用服务器。

使用 WebP 格式替代 JPEG/PNG 以减少 30-50% 的文件大小，配合 CDN 缓存实现毫秒级加载。

### 关键设计决策

1. **同步处理**: 选择上传时同步生成所有尺寸而非异步，因为头像上传频率低（每用户每月 < 1次），同步处理的 P95 < 2s 完全可接受，且避免了异步带来的一致性问题（用户上传后看到旧头像）。
2. **WebP 优先**: 选择 WebP 格式存储而非保留原格式，因为同等画质下 WebP 比 JPEG 小 30%、比 PNG 小 50%，CDN 带宽成本直接降低。
3. **CDN URL 直出**: 选择数据库存储 CDN URL 而非存储键再拼接，因为避免了每次读取时的 URL 计算，查询结果可以直接返回给前端。

### 架构概要

```
上传热路径（低频，可以稍慢）:
  Controller → validate(5ms) → sharp.resize(200ms) → S3.upload(500ms) → DB.update(5ms)
  总 P95: < 800ms

加载热路径（高频，必须快）:
  Browser → CDN (cache hit: 5ms, miss: 50ms)
  应用服务器完全不参与
```

关键指标预估：
- 上传 P95: < 800ms（3 个尺寸并行处理）
- 加载 P95: < 50ms（CDN 命中后 < 5ms）
- 存储成本: ~¥0.08/GB/月（WebP 比 JPEG 节省 30%）

### 优势

- 用户上传后立即看到所有尺寸的新头像，无一致性延迟
- 头像加载走 CDN，P95 < 50ms，应用服务器零负载
- WebP 格式减少 30-50% 存储和带宽成本

### 已知代价与风险

- 同步处理使上传接口 P95 达到 800ms，比纯存储方案慢约 500ms
- 直接使用 S3 SDK，更换存储后端需要修改业务代码
- WebP 在极老的浏览器（IE11）上不支持，需要降级策略

### 与其他视角的预期分歧

- 架构师可能认为: 直接依赖 S3 SDK 破坏了存储抽象，未来切换存储后端成本高
- 资深开发可能认为: WebP 格式转换增加了不必要的复杂度，JPEG/PNG 已经够用

## 资深开发方案: 最小可用方案

### 核心策略

用最少的代码和最直接的方式实现头像功能。直接使用 S3 SDK 上传原图 + 一个标准缩略图（200x200），不做格式转换，不做多尺寸。前端用 CSS 控制显示大小。先跑通核心流程，后续根据实际需要迭代优化。

### 关键设计决策

1. **只生成一个缩略图**: 选择只生成 200x200 缩略图而非多个尺寸，因为前端可以用 CSS 的 `object-fit` 适配不同场景，多尺寸缩略图是过早优化。
2. **保留原格式**: 选择保留 JPEG/PNG 原格式而非转 WebP，因为浏览器兼容性更好、实现更简单、省去格式转换的复杂度。
3. **复用现有中间件**: 选择在现有的 `multer` 文件上传中间件上扩展，而非引入新的文件处理流程，因为团队已经熟悉这套模式。

### 架构概要

```
现有代码:
  routes/users.ts → controllers/userController.ts → services/userService.ts

新增:
  routes/users.ts        + POST /:id/avatar, DELETE /:id/avatar
  services/avatarService.ts  新建, ~100行（validate + resize + upload + cleanup）
  config/s3.ts           新建, ~30行（S3 客户端配置）
```

新增代码量预估: ~200行（含测试），修改现有代码 ~20行。
预计开发时间: 1 天。

### 优势

- 代码量最少（~200行新代码），实现最快（1天）
- 复用现有模式（multer），团队无学习成本
- 核心流程简单直接，出问题容易排查

### 已知代价与风险

- 只有一个缩略图尺寸，如果后续需要多尺寸要重新做图片处理逻辑
- 无 CDN 配置（一期直接走 S3 公开 URL），大流量时加载速度受限
- S3 SDK 直接调用散落在 avatarService 中，后续难以替换存储后端

### 与其他视角的预期分歧

- 架构师可能认为: 没有存储抽象层，代码耦合度过高，后续扩展成本大
- 性能专家可能认为: 不走 CDN、不做 WebP 优化，加载性能远未达到最优

## 技术负责人方案对比

### 对比矩阵

| 维度 | 架构师方案 | 性能专家方案 | 资深开发方案 |
|------|-----------|------------|------------|
| 架构合理性 | 高 / 分层清晰，存储和处理可替换 | 中 / 直接依赖 S3 SDK，但关注点分离合理 | 低 / 逻辑集中在单一 service，耦合度高 |
| 性能表现 | 中 / 异步处理有一致性延迟 | 高 / CDN 直推，WebP 优化，量化指标清晰 | 中 / 无 CDN，无格式优化，但满足底线 |
| 开发成本 | 高 / 约 3 天，需要定义接口和实现 | 中 / 约 2 天，WebP 和 CDN 配置有工作量 | 低 / 约 1 天，复用现有模式 |
| 可维护性 | 高 / 模块独立，新人容易理解结构 | 中 / 性能优化代码需要一定理解成本 | 高 / 代码简单直观，但扩展时需重构 |
| 风险程度 | 低 / 成熟模式，风险可控 | 中 / WebP 兼容性、CDN 配置有一定风险 | 低 / 简单方案，风险最低 |

### 推荐方案

推荐 **性能专家方案: 同步流水线 + CDN 直推**

### 推荐理由

1. **性能指标最优且量化清晰** — 头像加载是高频操作，CDN 直推将 P95 从百毫秒级降到个位数毫秒，用户体验提升显著
2. **同步处理避免一致性问题** — 头像上传低频，800ms 的上传延迟完全可接受，换来"上传即可见"的确定性
3. **成本收益平衡** — 2 天开发时间中等，但 WebP + CDN 在运行成本上长期节省

### 交叉借鉴

- 从 **架构师方案** 借鉴 StorageProvider 接口思路：不做完整抽象层，但将 S3 调用封装到独立文件 `s3-client.ts` 中，未来替换只改一处
- 从 **资深开发方案** 借鉴 multer 复用：上传中间件继续用 multer，不引入新的文件处理框架
