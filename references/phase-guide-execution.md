## Phase 4: 设计 (Standard及以上)

### 目标

记录技术决策和权衡，让将来的维护者理解"为什么这样做"。

### 设计文档结构

创建 `docs/spec-power/changes/<change-name>-YYYYMMDDHHMMSS/design.md`

#### 现状
当前系统相关部分如何工作，架构背景

#### 目标与非目标
明确追求什么、不追求什么

#### 方案对比

至少包含2个方案：

**方案 A: <名称> (推荐)**
- 核心思路
- 优势
- 劣势
- 实现复杂度: 低/中/高

**方案 B: <名称>**
- 核心思路
- 优势
- 劣势

#### 决策
选择方案 A，因为<具体理由>

#### 关键设计细节
- 数据模型
- 接口定义（精确到参数和返回值）
- 错误处理策略

#### 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| ... | 低/中/高 | 低/中/高 | ... |

#### 迁移计划（如需）
分步部署策略和回滚方案

### 设计自审

- [ ] 至少考虑了2个方案（即使另一个明显不如）
- [ ] 决策理由具体——不是"更好"而是"因为X所以Y"
- [ ] 接口定义精确到参数和返回值
- [ ] 识别了至少一个风险

完整模板见 `artifact-system.md`

### Strict 模式：多角色方案对比

Standard 模式的"2+ 方案对比"由同一个设计者产出，容易形成"推荐方案 + 陪跑方案"。Strict 模式处理关键系统，需要从不同优化目标出发产出真正有竞争力的替代方案。

#### 为什么三个角色会产生不同的方案

三个角色的优化目标存在真实冲突，这正是多角色的价值：

| 架构师倾向 | 性能专家倾向 | 资深开发倾向 |
|-----------|------------|------------|
| 多加抽象层以解耦 | 减少抽象层以降低延迟 | 够用就行，别过度设计 |
| 接口标准化、扩展预留 | 热路径特化、减少间接调用 | 接口简单直接，快速交付 |
| 事件驱动解耦模块 | 同步调用减少复杂度 | 先跑通再说，迭代优化 |
| 分布式架构预留 | 内存局部性、缓存策略 | 单体先行，复杂度可控 |

#### 流程

```
步骤1: [主设计者] 产出共享上下文（现状 + 目标 + 非目标 + 硬约束）
         ↓
步骤2: [三角色并行] 基于共享上下文，各出聚焦方案（dispatch 3个子agent）
         ↓
步骤3: [技术负责人] 5维度对比矩阵 + 推荐方案 + 推荐理由
         ↓
步骤4: [用户评审] 选择最终方案（结构化选项）
         ↓ (不通过则回到步骤2修订)
步骤5: [设计定稿] 将选定方案展开为完整 design.md
```

#### 步骤1：共享上下文

主设计者产出一份共享上下文，三个角色共用（避免重复劳动）：

```markdown
## 共享上下文

### 现状
<当前系统相关部分如何工作>

### 目标
- <目标 1>
- <目标 2>

### 非目标
- <明确不追求的目标>

### 硬约束
- 技术栈: <不可变的技术选型>
- 兼容性: <必须保持的兼容性>
- 性能底线: <不可低于的性能指标>
- 其他约束: <团队规模、上线时间等>
```

#### 步骤2：三角色聚焦方案

每个角色产出聚焦方案（~60-80行），重点是差异化的技术选型和决策，而非重复共享上下文。

**角色定义**：
- **架构师**：系统分层、模块解耦、可扩展性、长期可维护性
- **性能专家**：响应速度、内存占用、IO优化、并发处理、瓶颈预防
- **资深开发**：开发效率、代码简洁、快速上线、技术债务控制

**聚焦方案格式**：

```markdown
## [角色名] 方案: <方案名称>

### 核心策略
<2-3段话说清整体思路和技术选型，从本角色优化目标出发>

### 关键设计决策
1. **[决策点1]**: 选择 X 而非 Y，因为 <从本角色优化目标出发的理由>
2. **[决策点2]**: ...
3. **[决策点3]**: ...

### 架构概要
<核心模块划分、数据流、关键接口>
（聚焦架构层面，不需要完整的接口参数定义）

### 优势（从本角色视角）
- ...

### 已知代价与风险
- ...（诚实承认本方案在其他维度上的牺牲）

### 与其他视角的预期分歧
- 架构师可能认为...
- 性能专家可能认为...
- 资深开发可能认为...
```

最后一节"预期分歧"迫使每个角色提前思考其他视角的反对意见，避免盲目自信。

**子agent提示模板**：见 `agents/architect.md`、`agents/perf-expert.md`、`agents/senior-dev.md`

#### 步骤3：技术负责人对比

主agent 以技术负责人视角，用5个维度对三份方案进行结构化对比：

```markdown
## 技术负责人方案对比

### 对比矩阵

| 维度 | 架构师方案 | 性能专家方案 | 资深开发方案 |
|------|-----------|------------|------------|
| 架构合理性 | <评级> / <关键说明> | <评级> / <关键说明> | <评级> / <关键说明> |
| 性能表现   | <评级> / <关键说明> | <评级> / <关键说明> | <评级> / <关键说明> |
| 开发成本   | <评级> / <关键说明> | <评级> / <关键说明> | <评级> / <关键说明> |
| 可维护性   | <评级> / <关键说明> | <评级> / <关键说明> | <评级> / <关键说明> |
| 风险程度   | <评级> / <关键说明> | <评级> / <关键说明> | <评级> / <关键说明> |

### 推荐方案
推荐 **[方案名]**

### 推荐理由
1. <具体理由，说明为什么该方案在当前场景下的优势最关键>
2. ...
3. ...

### 交叉借鉴（可选）
从其他方案中吸收的有价值设计点：
- 从 [方案X] 借鉴 <具体设计点>
- ...
```

**对比维度说明**：
- **架构合理性**：分层是否清晰、模块职责是否单一、扩展性如何
- **性能表现**：预期的响应时间、内存占用、是否有性能瓶颈
- **开发成本**：实现难度、开发周期、团队学习成本
- **可维护性**：代码复杂度、测试友好性、后续迭代成本
- **风险程度**：技术风险、集成风险、上线风险

#### 步骤4：用户评审

向用户展示：共享上下文 + 三份聚焦方案 + 对比矩阵 + 推荐。提供结构化选项：

1. **同意推荐方案** — 直接按推荐方案展开完整设计
2. **选择其他方案** — 指定选哪个，可附修改意见
3. **混合方案** — 指定从各方案中取哪些元素
4. **都不满意，重新修订** — 说明方向后三角色重新产出

#### 步骤5：设计定稿

用户选定后，主设计者将选定方案展开为完整的 `design.md`（模板不变：数据模型、精确接口定义、错误处理、风险缓解、迁移计划等）。

#### 无子agent降级

主agent 顺序扮演三个角色，每次切换时明确声明：

> 现在切换到 **性能专家** 视角。从响应速度、内存占用、IO优化角度重新审视这个问题...

产出格式不变。效果不如并行子agent（后续角色会受前面影响），但仍优于单一视角。

## Phase 5: 任务分解 (Standard及以上)

### 目标

将设计转化为可执行的小任务。

**任务粒度建议**: 单个任务 5-15 分钟为佳，不超过 30 分钟。
- **过小的风险**（<2分钟）：任务数爆炸、上下文切换成本高于执行成本、commit 历史混乱
- **过大的风险**（>30分钟）：失去快速验证的反馈、难以隔离问题、一次性修改太多难以审查

**灵活调整**: 根据任务复杂度调整粒度。简单任务可以合并（如"添加5个类似的getter函数"），复杂任务必须拆细（如"实现完整的认证流程"应拆成多个任务）。

### 任务文档结构

创建 `docs/spec-power/changes/<change-name>-YYYYMMDDHHMMSS/tasks.md`

#### 前言部分

```markdown
**目标**: 一句话
**架构**: 2-3句话概括
**技术栈**: 关键技术
```

#### 任务模板

```markdown
## Task N: <组件名>

**文件**:
- Create: `src/path/to/new-file.ts`
- Modify: `src/path/to/existing.ts`
- Test: `tests/path/to/test.ts`

**依赖**: 无 (可并行) | Task X (需要其接口)

**步骤**:
- [ ] 编写失败测试: <具体描述测试什么>
  验证: `npm test -- --grep 'keyword'` → 期望失败
- [ ] 验证RED: 失败原因是"功能未实现"而非语法错误
- [ ] 最小实现使测试通过
  验证: `npm test` → 期望全部通过
- [ ] 验证GREEN: 运行完整测试套件
- [ ] 重构（如需）
  验证: 保持测试绿色
- [ ] 提交: `git commit -m "feat: <具体说明>"`
```

### 任务分解规则

1. **独立可验证**: 每个任务完成后有明确的"通过/不通过"判定
2. **文件映射精确**: Create/Modify/Test三种操作，精确到路径
3. **依赖标注清楚**: 无依赖的任务标注"可并行"
4. **无占位符**: 不允许"添加验证逻辑"，要写"验证email格式匹配RFC 5322"
5. **每步含验证命令**: 包含具体的命令和预期结果

### 依赖图可视化

```
Task 1 ──► Task 3
Task 2 ──► Task 3
Task 3 ──► Task 4

可并行: Task 1, Task 2
```

### 任务自审

- [ ] 所有设计文档中的组件都有对应任务
- [ ] 任务依赖关系形成DAG（无循环）
- [ ] 无依赖的任务已标注"可并行"
- [ ] 每个任务都以测试开始（TDD）

完整模板见 `artifact-system.md`

## Phase 6: 执行与逐任务审查

### 目标

产出经过TDD验证的代码实现。Standard+ 模式下每个任务完成后立即通过审查门控。

### 模式差异

| 模式 | 执行方式 | 审查方式 |
|------|---------|---------|
| **Flow** | 直接 TDD 执行 | 自我审查（30秒清单）即可，无需子agent审查 |
| **Standard** | 逐任务 TDD + 逐任务审查 | 自我审查 + 代码质量审查（子agent） |
| **Strict** | 逐任务 TDD + 逐任务审查 | 自我审查 + 规范符合审查 + 代码质量审查（子agent） |

Flow 模式的执行细节见 `flow-mode-guide.md`，以下内容主要面向 Standard+ 模式。

### 执行方式选择（Standard+）

**子agent并行**（Claude Code，推荐）:
- 每个无依赖任务dispatch一个子agent（Fresh subagent per task，零上下文污染）
- 控制器提前提取任务全文，直接注入 prompt（子agent不应自行读取 tasks.md）
- 主agent监控进度和集成

**内联顺序**（Cursor/Copilot/其他）:
- 按依赖顺序逐个执行任务
- 同样遵循TDD流程和逐任务审查
- 适合无子agent支持的平台

### 逐任务循环

每个任务必须完整通过此循环后才能标记完成：

```
┌─────────────────────────────────────────────────────────────────┐
│  Step 1: 实现（TDD: RED → 验证RED → GREEN → 验证GREEN → REFACTOR） │
│       ↓                                                          │
│  Step 2: 自我审查（30秒）                                          │
│       代码完整性 + 测试覆盖 + 安全基线                                │
│       ↓                                                          │
│  Step 3: 规范符合审查（Strict，子agent）                              │
│       对比 specs/ 检查覆盖和正确性                                    │
│       ↓                                                          │
│  Step 4: 代码质量审查（Standard+，子agent）                           │
│       架构、质量、安全、可维护性                                       │
│       ↓                                                          │
│  Step 5: 修复→重审闭环（如有问题）                                    │
│       Critical/Important → 修复 → 重新审查 → 循环（最多3轮）          │
│       Suggestion → 记录，不阻塞                                     │
│       ↓                                                          │
│  Step 6: 验证通过 → 提交 → 标记任务完成                               │
└─────────────────────────────────────────────────────────────────┘
```

### TDD铁律

详见 `execution-guide.md` — TDD 完整流程。

### 验证纪律

**任何声称完成的时刻都必须有新鲜的验证证据。** 不是"我认为测试应该通过"，而是"我运行了测试，输出如下"。

> 完整的验证门函数、反合理化表格和 Red Flags 信号见 `mindset.md` - 验证纪律章节。

### 逐任务审查详解

#### 自我审查（30秒，所有模式）

每完成一个任务立即执行：

**代码完整性**:
- 无TODO/FIXME/HACK遗留
- 无注释掉的代码
- 无调试用临时代码

**测试覆盖**:
- 正常路径有测试
- 边界情况有测试
- 错误路径有测试

**安全基线**:
- 用户输入有验证和清洗
- 无SQL拼接（使用参数化查询）
- 无XSS风险（输出有转义）
- 敏感信息未暴露在日志或错误消息中
- 无硬编码密钥或凭证

详细清单见 `review-verify.md`

#### 规范符合审查（仅Strict，子agent）

Dispatch `spec-reviewer` 子agent：
- 对比specs/中的每个Requirement和Scenario
- 检查实现是否完整覆盖所有规范要求
- 标记偏差——是改进还是遗漏
- **不信任实现者的报告** — 必须独立阅读代码验证

详见 `agents/spec-reviewer.md` 和 `review-verify.md`

#### 代码质量审查（Standard+，子agent）

**前提条件**: 仅在规范符合审查通过后才执行（Strict 模式）。先确认做的是对的东西，再确认做的东西是好的。如果 spec 审查未通过就开始 code 审查，reviewer 可能审查即将被修改的代码，浪费资源。

Dispatch `code-reviewer` 子agent：
- 架构设计合理性
- 代码风格与项目约定一致
- 错误处理完善
- 无过度工程或过少工程
- 问题分级：Critical / Important / Suggestion

详见 `agents/code-reviewer.md` 和 `review-verify.md`

### 修复→重审闭环

审查发现问题后的处理流程：

```
审查发现问题
     ↓
┌── Critical / Important ──────────────────────┐
│   实现者修复                                    │
│        ↓                                       │
│   审查者重新审查（不信任"已修复"声明）              │
│        ↓                                       │
│   通过? ── 是 → 继续下一步                       │
│        └── 否 → 再次修复（第2轮）                 │
│                  ↓                              │
│             通过? ── 是 → 继续                   │
│                  └── 否 → 再次修复（第3轮）        │
│                           ↓                     │
│                      通过? ── 是 → 继续          │
│                           └── 否 → 升级给用户     │
└─────────────────────────────────────────────────┘

┌── Suggestion ───────┐
│   记录，不阻塞        │
│   由用户决定是否处理    │
└─────────────────────┘
```

**关键原则**:
- 审查者必须**重新审查修复后的代码**
- 最多3轮修复循环，超过则升级给用户决策
- 对审查意见做技术评估，不要表演性同意。如果审查意见有误，说明为什么

### 子agent调度

详见 `execution-guide.md` 的"子agent调度"章节和 `agents/implementer.md`

### 模型选择策略

| 任务类型 | 推荐模型 | 信号 |
|---------|---------|------|
| 机械实现（明确spec，1-2文件） | 轻量模型 | 成本效率 |

遇到问题时使用四阶段法：
1. 根因调查
2. 假设形成
3. 验证
4. 修复

详见 `execution-guide.md` 的"系统调试四阶段"

## Phase 7: 全局审查 (Standard及以上)

### 目标

所有任务完成后，从全局视角检查跨任务一致性和整体质量。Phase 6 的逐任务审查捕获单任务内的问题，Phase 7 捕获**任务间的集成问题**。

### 审查内容

**跨任务接口一致性**:
- 不同任务产出的接口是否正确对接
- 数据结构在各模块间是否一致
- 错误处理模式是否统一

**整体架构评估**:
- 所有变更组合后的架构是否合理
- 是否引入了不必要的复杂性
- 模块间耦合度是否可接受

**交叉影响检查**:
- 确认 Phase 6 各任务的测试在集成后仍全部通过（如有疑虑可提前运行，完整测试运行在 Phase 8 执行）
- 检查是否存在 Phase 6 逐任务审查未覆盖的跨任务交互问题

**小变更补位审查**（审查阈值补偿）:
- 回顾所有在 Phase 6 中因低于阈值而跳过子agent审查的变更
- 检查多个小变更组合是否产生集成问题
- 验证跳过审查的变更中是否存在遗漏的强制例外情况（安全/SQL/并发等）

**代码风格一致性**:
- 不同子agent产出的代码风格是否统一
- 命名约定是否一致

### 审查结果处理

- **Critical**: 必须修复，阻塞完成
- **Important**: 应该修复，除非有充分理由不修
- **Suggestion**: 记录但不阻塞，由用户决定

对每个审查意见做技术评估，不要表演性同意。如果审查意见有误，说明为什么。

### 修复闭环

全局审查发现 Critical/Important 问题后：

```
发现问题 → 修复代码 → 重跑全量测试 → 重新全局审查
  └── 最多2轮循环，超过则升级给用户决策
```

与 Phase 6 逐任务闭环不同，全局审查的修复往往涉及多个文件的协调修改，因此循环次数更少（2轮 vs 3轮），更快升级给用户。

## Phase 8: 验证

### 目标

提供可验证的证据，证明变更达到了预期效果。

### 验证原则

1. **运行而非声称**: 不是"我认为测试应该通过"，而是"我运行了测试，结果如下"
2. **完整而非抽样**: 运行全部测试套件，不只是新增的
3. **真实而非模拟**: 如果可以集成测试，优先于mock
4. **捕获输出**: 把运行结果作为证据

### 验证清单

**必选项（所有模式）**:
- [ ] 运行完整测试套件，附上完整输出
- [ ] 新增测试数量和覆盖内容
- [ ] 无跳过(skip)的测试

**Standard+额外项**:
- [ ] 构建成功（如适用）
- [ ] Lint通过（如适用）
- [ ] 类型检查通过（如适用）

**Strict额外项**:
- [ ] 所有规范场景都有对应通过的测试
- [ ] 性能基准测试（如有要求）
- [ ] 安全扫描（如有要求）

### 验证报告格式

```markdown
## 验证结果

### 自动化测试
命令: `npm test`
结果:
```
通过: 47 | 失败: 0 | 跳过: 0
```
新增: 5个测试

### 构建验证
命令: `npm run build`
结果: 成功，无警告

### 手动验证（如适用）
- [x] 创建用户 → 返回201，数据正确
- [x] 重复邮箱 → 返回409，错误信息友好
```

### 行为变更记录（Standard+，验证通过后）

验证通过后，评估本次变更是否修改了已有行为（不仅是新增）：

**触发条件**: 本次变更涉及的模块在 `docs/spec-power/specs/` 中已有主规范，且实现修改了已有行为（而非纯新增）。如果不确定是否修改了已有行为，默认生成——宁多勿漏。

**产出**: 在变更目录生成 `behavior-changes.md`，格式如下：

```markdown
## 行为变更摘要

### 模块: <domain>
- <变更描述：什么从什么变成了什么>

### 模块: <domain>
- <变更描述>
```

**要求**:
- 自然语言描述，无需 Scenario 格式或 RFC 2119 关键词
- 聚焦"之前→之后"的行为差异，不描述实现细节
- 耗时应 < 2 分钟

## 阶段回退协议

当发现当前阶段的前提假设错误，需要回退重做时。

### 何时触发回退

| 发现时机 | 问题类型 | 回退到 | 示例 |
|---------|---------|--------|------|
| Phase 4 设计 | 需求理解错误 | Phase 1.5 | "用户实际需要的是 X 而非 Y" |
| Phase 6 执行 | 任务分解有问题 | Phase 5 | "任务粒度太大，无法完成" |
| Phase 6 执行 | 设计方案不可行 | Phase 4 | "接口设计在实际实现时发现有致命缺陷" |
| Phase 7 全局审查 | 规范缺失关键场景 | Phase 3 | "发现遗漏了并发冲突场景" |
| Phase 7 全局审查 | 某任务代码需重做 | Phase 6 | "跨任务接口不一致，需重新实现某个任务" |
| Phase 8 验证 | 功能不工作 | Phase 6 | "全量测试发现逐任务审查未覆盖的集成问题" |

### 回退流程

1. **识别回退点** — 明确需要回到哪个阶段
2. **保留已有工作** — 将当前工件重命名为 `.old` 备份
3. **更新状态** — 修改 `.specpower.yaml` 中对应工件状态为 `blocked`
4. **重新执行** — 从回退点开始，考虑已知问题
5. **对比验证** — 完成后与 `.old` 版本对比，确认问题已解决

### 回退不是失败

回退是发现问题的正常响应。记录回退原因到 `RETROSPECTIVE.md`，帮助改进流程。

详见 `review-verify.md`
