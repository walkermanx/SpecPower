# 审查与验证指南

## 三层质量网

SpecPower 使用三层递进式质量保障。每一层捕获不同类型的问题。

**Standard+ 模式下，三层审查内嵌在 Phase 6 的逐任务循环中**——每完成一个任务立即审查，而非所有任务完成后批量审查。Phase 7 全局审查则从跨任务视角补充检查。

```
Phase 6 逐任务审查（每个任务完成后立即执行）:
  第一层: 自我审查 (30秒, 即时, 所有模式)
    捕获: 明显遗漏、占位符、基础安全问题
         ↓
  第二层: 规范符合审查 (子agent, Strict 模式)
    捕获: 实现与规范的偏差、遗漏的需求、行为不一致
         ↓ （通过后才执行第三层）
  第三层: 代码质量审查 (子agent, Standard+ 模式)
    捕获: 架构问题、代码风格、错误处理、可维护性
         ↓
  修复→重审闭环 (Critical/Important 最多3轮)

Phase 7 全局审查（所有任务完成后）:
  跨任务接口一致性、整体架构、代码风格统一
```

## 第一层: 自我审查

每完成一个任务立即执行，不超过 30 秒。这是成本最低但回报率极高的质量手段。

### 自审清单

**代码完整性**:
- [ ] 没有 TODO、FIXME、HACK、XXX 注释遗留
- [ ] 没有被注释掉的代码块
- [ ] 没有 `console.log` 或调试用临时代码
- [ ] 没有硬编码的魔数或字符串（该提取为常量的）
- [ ] 没有 placeholder 值（如 `*-placeholder`、`your-*-here`、`REPLACE_ME`、`fake-token` 等假值占位符）

**测试覆盖**:
- [ ] 正常路径有测试
- [ ] 边界情况有测试（空值、极大值、并发）
- [ ] 错误路径有测试（无效输入、网络失败）

**安全基线**:
- [ ] 用户输入有验证和清洗
- [ ] 没有 SQL 拼接（使用参数化查询）
- [ ] 没有 XSS 风险（输出有转义）
- [ ] 敏感信息没有暴露在日志或错误消息中
- [ ] 没有硬编码的密钥或凭证

**一致性**:
- [ ] 命名风格与项目现有代码一致
- [ ] 文件组织与项目结构一致
- [ ] 错误处理模式与项目约定一致

### 自审心态

自审不是走形式。你刚写完的代码最容易有盲点——你的大脑会自动"填补"你认为写了但实际没写的逻辑。所以：

1. **重读代码而非回忆** — 不要回忆"我写了什么"，而是重新读一遍代码看"写了什么"
2. **质疑边界** — 每个 if 条件问一次"另一种情况呢？"
3. **检查错误路径** — 每个外部调用（数据库、API、文件）问一次"失败了会怎样？"

## 第二层: 规范符合审查

Dispatch `spec-reviewer` 子agent，让独立视角检查实现是否完整覆盖规范。

### 审查范围

对 `specs/` 目录下的每个需求和场景：

1. **覆盖性** — 这个需求是否已实现？
2. **正确性** — 实现的行为是否与规范描述一致？
3. **场景验证** — 每个 Scenario 是否有对应的测试用例？
4. **关键词遵循** — MUST 级需求是否被严格遵循？SHOULD 级呢？

### 审查输出格式

```markdown
## 规范符合审查报告

### 覆盖总结
- 总需求数: 12
- 已覆盖: 11
- 未覆盖: 1
- 覆盖率: 92%

### 偏差报告

#### [Critical] Requirement: 会话过期
**规范**: 系统 MUST 在 30 分钟不活动后过期会话
**实现**: 未找到超时检查逻辑
**建议**: 在 session middleware 中添加 idle timeout 检查

#### [Important] Requirement: 错误消息国际化
**规范**: 系统 SHOULD 返回本地化的错误消息
**实现**: 错误消息全部硬编码为英文
**建议**: 使用 i18n 框架包装错误消息

### 确认通过
- [x] Requirement: 用户注册 — 完整实现，3个场景全部覆盖
- [x] Requirement: 密码强度 — 完整实现，边界情况已覆盖
```

### 偏差分类

并非所有偏差都是问题。审查时区分：

- **遗漏** — 规范要求但未实现 → 通常需要修复
- **偏离** — 实现的行为与规范不同 → 判断是改进还是错误
- **超出** — 实现了规范未要求的功能 → 评估是否有必要

## 第三层: 代码质量审查

Dispatch `code-reviewer` 子agent，从代码质量角度审查所有变更。

### 审查维度

#### 1. 架构设计
- 职责清晰：每个模块/类/函数做一件事
- 依赖方向：高层不依赖低层实现细节
- 接口设计：最小化公开 API 面
- 耦合度：模块间通过接口交互，不直接访问内部状态

#### 2. 代码质量
- 可读性：命名清晰，逻辑流程直观
- DRY：无不必要的重复（但三行相似代码比过早抽象好）
- 错误处理：所有外部调用有适当的错误处理
- 类型安全：利用类型系统防止运行时错误

#### 3. 性能
- 无明显的 N+1 查询
- 无不必要的内存分配
- 适当的缓存策略（如有性能要求）
- 异步操作正确使用（无阻塞主线程）

#### 4. 安全性
- OWASP Top 10 检查
- 权限检查完整
- 数据验证在系统边界

#### 5. 可维护性
- 函数长度合理（<50行为佳）
- 嵌套层级合理（<4层）
- 注释解释"为什么"而非"什么"
- 测试可维护（不脆弱，不依赖实现细节）

### 审查输出格式

```markdown
## 代码质量审查报告

### 总体评估
代码质量: 良好
主要关注: 错误处理一致性

### 问题列表

#### [Critical] SQL注入风险
**文件**: `src/users/repository.ts:45`
**代码**: `db.query(\`SELECT * FROM users WHERE name = '${name}'\`)`
**问题**: 用户输入直接拼接到SQL语句
**修复**: 使用参数化查询 `db.query('SELECT * FROM users WHERE name = $1', [name])`

#### [Important] 缺少错误处理
**文件**: `src/users/service.ts:23`
**代码**: `const user = await repository.findById(id)`
**问题**: 未处理 user 为 null 的情况
**修复**: 添加 null 检查，返回 404

#### [Suggestion] 命名改进
**文件**: `src/users/controller.ts:15`
**代码**: `const d = await service.getData()`
**建议**: 重命名为 `const userData = await service.getUserData()`

### 亮点
- 良好的关注点分离
- 测试覆盖充分
- 一致的错误处理模式（除了上述指出的遗漏）
```

## 问题分级标准

| 级别 | 含义 | 处理方式 | 示例 |
|------|------|---------|------|
| **Critical** | 安全漏洞或数据损坏风险 | 必须修复，阻塞完成 | SQL注入、XSS、数据竞争 |
| **Important** | 功能缺陷或维护性问题 | 应该修复，除非有充分理由 | 缺少错误处理、测试遗漏 |
| **Suggestion** | 改进建议 | 不阻塞，由用户决定 | 命名改进、代码组织 |

### 处理审查反馈

对每个审查意见做**技术评估**，不要表演性同意：

- **同意并修复** — 问题确实存在，修复它
- **同意但延后** — 问题存在但不在当前范围，记录为 TODO
- **不同意并说明** — 审查意见有误，解释为什么当前实现是对的

不要为了取悦审查者而改代码。如果审查意见错了，说出来。

## 验证

**验证纪律是贯穿全流程的。** 任何声称完成的时刻——一个任务、一次修复、整个变更——都必须有新鲜的验证证据支撑。本章是验证纪律的**权威源**——具体做什么、怎么做、什么时候做都在这里。其他文档若提到"验证纪律",应指向此处而非独立描述。

### 核心铁律

```
没有新鲜验证证据的完成声明 = 谎言
```

如果你没有在**这次操作中**运行验证命令，你不能声称它通过了。"刚才运行过"不算——改过代码就要重新运行。

### 验证原则

1. **运行而非声称** — 不是"我认为测试应该通过"，而是"我运行了测试，结果如下"
2. **完整而非抽样** — 运行全部测试套件，不只是新增的
3. **真实而非模拟** — 如果可以集成测试，优先于 mock
4. **捕获输出** — 把运行结果贴出来作为证据

**禁止伪造验证**：在代码注释或文档里写"模拟结果：✅ 14/14 通过"不是验证证据，等同于没有验证。如果当前环境无法运行测试（无项目依赖、沙箱限制等），正确的做法是**明确说明**："当前无可运行环境，无法提供执行级验证证据（B/C 级），需在真实环境验证后补充。" 用户宁愿知道真相，也不愿看到虚假的绿灯。

### 验证门函数（5 步）

在声称任何状态或表达满意之前：

```
1. 确认: 什么命令能证明这个声明？
2. 运行: 执行完整的命令（新鲜的、完整的）
3. 阅读: 完整输出、检查退出码、计数失败
4. 核实: 输出是否确认了你的声明？
   - 否 → 陈述实际状态及证据
   - 是 → 陈述声明并附上证据
5. 然后才能: 发表声明

跳过任何一步 = 没有验证
```

### 反合理化：借口与现实

| 借口 | 现实 |
|------|------|
| "应该没问题了" | 运行验证命令 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次跳过" | 没有例外 |
| "Lint 通过了" | Lint ≠ 编译 ≠ 测试通过 |
| "子agent说成功了" | 独立验证，不信任报告 |
| "太累了不想跑了" | 疲劳不是借口 |
| "部分检查够了" | 部分什么也证明不了 |
| "刚才运行过了" | "刚才" ≠ "现在"，改过代码就要重新运行 |
| "我手动测试过了" | 手动不可重复、不可追溯 |
| "这个改动太小了" | 小改动也能引入大 bug |

### 常见验证失败对照

按场景对照"需要什么证据"和"什么证据不够"：

| 声明 | 需要的证据 | 不够的证据 |
|------|-----------|-----------|
| 测试通过 | 测试命令输出: 0 failures | 之前的运行结果、"应该通过" |
| Lint 干净 | Lint 输出: 0 errors | 部分检查、推测 |
| 构建成功 | 构建命令: exit 0 | Lint 通过就行、日志看起来对 |
| Bug 已修 | 原始症状测试: 通过 | 代码改了就假设修了 |
| 回归测试有效 | Red-Green 循环验证 | 测试通过一次 |
| 子agent完成 | VCS diff 确认变更 | agent 报告"成功" |
| 需求满足 | 逐条对照清单 | 测试通过就够了 |

### Red Flags — 说出这些话时立即停下

- 使用 "should"、"able to"（模糊词）
- 使用 "probably"、"seems to"、"looks like"（推测词）
- 验证前表达满意（"完成了！"、"搞定！"、"没问题"）
- 即将提交/推送/创建 PR 但没运行验证
- 信任子agent报告而未独立验证
- 依赖部分验证得出整体结论
- 想着"就这一次跳过"
- 累了想赶紧结束
- **任何暗示成功但没有运行验证命令的措辞**

出现以上任何一条，执行上方"验证门函数"，不要继续。

### 什么时候应用验证门

**永远在以下时刻之前:**
- 声称任何成功/完成
- 表达满意（"完成了！"、"搞定！"）
- 提交代码
- 创建 PR
- 标记任务完成
- 移动到下一个任务

### 验证清单

#### 必选项 (所有模式)
- [ ] 运行完整测试套件，附上完整输出
- [ ] 新增测试数量和覆盖内容
- [ ] 无跳过(skip)的测试

#### Standard+ 额外项
- [ ] 构建成功（如适用）
- [ ] Lint 通过（如适用）
- [ ] 类型检查通过（如适用）

#### Strict 额外项
- [ ] 所有规范场景都有对应通过的测试
- [ ] 性能基准测试（如有要求）
- [ ] 安全扫描（如有要求）

### 验证报告模板

```markdown
## 验证结果

### 自动化测试
命令: `<实际运行的命令>`
结果:
```
<实际输出>
```
通过: X | 失败: 0 | 跳过: 0
新增: Y 个测试

### 构建验证
命令: `<实际运行的命令>`
结果: 成功/失败
警告: <列出警告，如有>

### 手动验证 (如适用)
- [x] <验证步骤 1> → <实际结果>
- [x] <验证步骤 2> → <实际结果>

### 规范覆盖 (Strict)
- 总场景数: X
- 已覆盖: Y
- 覆盖率: Z%
```

## 无子agent时的降级方案

当平台不支持子agent（Cursor、Copilot 等）时：

### 替代第二层（规范审查）
用结构化自审替代独立子agent：
1. 打开 specs/ 目录
2. 逐个需求检查：这个需求实现了吗？
3. 逐个场景检查：这个场景有测试吗？
4. 记录发现的偏差

### 替代第三层（代码审查）

用清单驱动的自审替代，但**输出格式必须与子agent版本相同**——没有书面输出的审查等于没有审查：

1. 对每个修改的文件，过一遍代码质量审查维度（见本文件"审查维度"章节）
2. 特别关注安全性维度（自审容易遗漏）
3. 使用 `git diff` 确保只审查变更部分
4. 将发现按"代码质量审查报告"格式写出来（总体评估 + 问题列表 + 亮点）

层 1 的自审清单（30秒）≠ 层 3 的代码质量审查——两者检查的角度不同。前者是快速完整性扫描，后者是架构/质量/安全的深度评估。降级时这两层都要做，也都要有书面输出。

自审的关键是**假装你是另一个人第一次看这段代码**。
