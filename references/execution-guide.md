# 执行指南

## TDD 完整流程

测试驱动开发是 SpecPower 执行阶段的核心纪律。

### TDD 适用范围

**必须遵循 TDD**:
- 任何业务逻辑（if/else、循环、算法）
- 数据处理（解析、转换、验证）
- API/接口修改（路由、参数、返回值）
- Bug 修复（必须先写复现测试）

**可以豁免 TDD**（但需要其他验证）:
- 纯配置文件修改（config.json, .env 等）→ 验证：运行系统观察配置生效
- 纯样式调整（CSS, SCSS 等）→ 验证：视觉检查 + 浏览器测试
- 文档修改（README, 注释等）→ 验证：渲染效果检查
- 基础设施脚本（部署脚本、构建配置）→ 验证：运行脚本确认功能
- 静态资源（图片、字体等）→ 验证：加载测试

**豁免不代表不验证** - 每种豁免场景都有对应的验证方法，只是不需要写自动化测试。

## Red-Green-Refactor 循环

```
┌──────────────────────────────────────────────────┐
│  RED: 写一个会失败的测试                          │
│       ↓                                           │
│  验证 RED: 运行测试，确认失败原因正确              │
│       ↓                                           │
│  GREEN: 写最少的代码使测试通过                     │
│       ↓                                           │
│  验证 GREEN: 运行全部测试，确认全部通过             │
│       ↓                                           │
│  REFACTOR: 改善代码结构，保持绿色                  │
│       ↓                                           │
│  回到 RED (下一个行为)                             │
└──────────────────────────────────────────────────┘
```

### RED 阶段详解

写一个测试，描述你期望的行为。这个测试必须失败。

```typescript
// 好的 RED — 测试一个具体行为
test('createUser returns 409 when email already exists', async () => {
  await createUser({ email: 'alice@example.com', name: 'Alice' });
  const result = await createUser({ email: 'alice@example.com', name: 'Bob' });
  expect(result.status).toBe(409);
  expect(result.body.error).toContain('already exists');
});
```

### 验证 RED

运行测试，检查失败原因。失败原因必须是"功能未实现"，而不是：
- 语法错误
- 导入错误
- 测试框架配置问题

如果失败原因不对，先修复测试本身。

### GREEN 阶段

写**最少**的代码让测试通过。不要提前优化，不要处理还没测试覆盖的边界情况。

```typescript
// 好的 GREEN — 最小实现
async function createUser(data) {
  const existing = await db.users.findByEmail(data.email);
  if (existing) {
    return { status: 409, body: { error: 'Email already exists' } };
  }
  const user = await db.users.insert(data);
  return { status: 201, body: user };
}
```

### 验证 GREEN

运行**全部**测试，不只是新写的那个。确保新代码没有破坏已有功能。

### REFACTOR 阶段

改善代码结构：提取函数、重命名变量、消除重复。每次修改后运行测试，保持绿色。

### 常见违规和纠正

| 违规 | 纠正 |
|------|------|
| 写了生产代码但没有对应测试 | 删掉代码，先写测试 |
| 测试失败原因是语法错误 | 修复测试语法，重新验证 RED |
| GREEN 阶段写了超出测试覆盖的代码 | 删掉多余代码，或补充测试 |
| REFACTOR 阶段加了新功能 | 回退，新功能走新的 RED-GREEN 循环 |
| 跳过了验证 RED | 回去运行测试，确认失败原因 |

## 子agent 调度

### 何时使用子agent

- 有 2+ 个无依赖的任务可并行
- 每个任务有明确的输入输出
- 任务之间不共享可变状态
- 平台支持子agent（Claude Code）

### 何时不用子agent并行

- **故障关联** — 多个失败可能源于同一根因，并行调查会重复劳动。先调查一个，确认是否独立再决定
- **共享状态** — 任务会编辑同一文件或使用同一资源，并行会产生冲突
- **探索性调试** — 还不清楚问题在哪，需要先建立全局理解再分工
- **强依赖链** — 任务 B 的输入是任务 A 的输出，无法并行

### Agent Prompt 常见错误

| 错误 | 示例 | 修正 |
|------|------|------|
| **太宽泛** | "修复所有测试" | "修复 auth.test.ts 中的 3 个失败用例" |
| **缺上下文** | "修复竞态条件" | 粘贴错误信息、测试名、相关代码路径 |
| **无约束** | "修好它" | "只修改 src/auth/，不动其他模块" |
| **输出模糊** | "搞定就行" | "返回根因分析 + 修改的文件列表 + 测试结果" |

### 调度流程

```
1. 读取 tasks.md，一次性提取所有任务的完整文本
2. 识别可并行的任务组
3. 为每个任务构造上下文丰富的 prompt（注入全文，而非让子agent读文件）
4. 并行 dispatch 子agent（每任务新建 fresh subagent）
5. 处理子agent提问（回答后重新dispatch）
6. 收集结果，进入逐任务审查（自审→规范审查→代码审查）
7. 审查通过后，集成代码
8. 进入下一组依赖任务
```

### 上下文隔离原则

- **每任务新建子agent** — Fresh subagent per task，零上下文污染。不要复用已完成任务的子agent
- **控制器提取全文注入** — 控制器提前从 tasks.md 提取任务全文，直接注入子agent prompt
- **子agent不应自行读取工件文件** — 不读 tasks.md、proposal.md 等。如需额外信息，报告 NEEDS_CONTEXT
- **原因**: 节省子agent上下文开销 + 避免读到不相关信息导致偏差 + 保持控制器对信息流的掌控

### 轻量注入原则

**核心目标**: 最小化子agent上下文消耗，只注入完成当前任务所需的信息。

**规则**:
1. **只注入相关片段** — 不传 design.md 全文，只传当前任务涉及的接口定义
2. **不传规范全文** — 只传当前任务对应的 spec 场景（如有）
3. **执行规则内联** — TDD 流程用 3 行摘要而非完整文档
4. **项目上下文复用** — 同批次并行的 agent 共享相同的层1，不重复构造

**注入量控制目标**:
- 实现者 agent: < 3000 tokens（任务定义 + 接口 + TDD摘要）
- 审查者 agent: < 2000 tokens（代码diff + 审查清单摘要）
- 设计者 agent: < 4000 tokens（现状 + 约束 + 目标）

### 上下文注入模板

每个子agent 收到的 prompt 包含四层上下文（按轻量原则裁剪）：

```
层1: 项目上下文（~500 tokens）
  - 技术栈、关键约定（一段话）
  - 来源: 控制器从项目配置中提炼摘要

层2: 任务上下文（~1500 tokens）
  - 具体任务描述（全文粘贴）、文件列表、验证命令
  - 来源: 控制器从 tasks.md 中提取当前任务（不让子agent读文件）

层3: 依赖上下文（~500 tokens，按需）
  - 仅当前任务涉及的接口定义、数据结构
  - 来源: 控制器从 design.md 中提取相关片段（非全文）

层4: 执行规则（~300 tokens）
  - TDD 三行摘要: "先写失败测试→最小实现→重构"
  - 输出约束: "只交付代码+测试结果+状态标识，不解释背景"
  - 来源: 内联（不需要读完整 execution-guide）
```

### 子agent 状态处理

子agent 可能报告以下状态：

| 状态 | 含义 | 处理方式 |
|------|------|---------|
| COMPLETED | 任务完成 | 收集结果，进入逐任务审查 |
| DONE_WITH_CONCERNS | 完成但有疑虑 | 主agent评估疑虑（见下方详解） |
| NEEDS_CONTEXT | 缺少上下文 | 补充信息重新 dispatch |
| BLOCKED | 遇到外部阻塞 | 评估是否可以解除（见下方升级策略） |
| FAILED | 测试持续失败 | 分析原因，可能需要调整任务 |

**DONE_WITH_CONCERNS 处理详解**:

实现者完成了工作但对某些方面有疑虑。主agent在进入审查前评估：
- **正确性/范围疑虑**（如"不确定这个边界条件处理是否正确"）→ 先处理疑虑再进入审查
- **观察性疑虑**（如"这个文件越来越大了"、"这个API感觉可以更简洁"）→ 记录后继续审查

**不要忽视 concerns** — 它们通常是实现者的直觉信号，值得评估。但也不要因为观察性疑虑阻塞流程。

**BLOCKED 升级策略**:

1. 如果是上下文问题 → 提供更多上下文，重新 dispatch（同一模型）
2. 如果任务需要更强推理 → 用更强模型重新 dispatch
3. 如果任务太大 → 拆分为更小的任务
4. 如果计划本身有问题 → 升级给用户

**永远不要**忽视升级信号或强制同一模型在没有改变的情况下重试。

### 模型选择策略 (如平台支持)

| 任务类型 | 推荐模型 | 原因 |
|---------|---------|------|
| 机械实现 | 轻量模型 | 成本效率 |
| 接口集成 | 标准模型 | 需要理解上下文 |
| 架构决策 | 最强模型 | 需要深度推理 |

### 审查阈值规则

并非所有变更都需要子agent审查。以下阈值帮助控制审查开销：

| 变更规模 | 审查方式 | 原因 |
|---------|---------|------|
| diff < 20 行 | 自审即可，跳过子agent | 小变更自审成本低，子agent注入开销不值得 |
| 20-100 行 | 自审 + 代码审查 | 中等变更需要独立视角 |
| 100+ 行 | 自审 + 规范审查 + 代码审查 | 大变更需要完整三层 |
| 纯配置/文档 | 自审即可 | 无逻辑变更不需要代码审查 |

**例外**: 即使 diff 小，以下情况仍需子agent审查：
- 安全相关变更（认证、授权、加密）
- 核心数据结构变更
- 公开 API 签名变更

## 系统调试四阶段

遇到 bug 或测试失败时，遵循这四个阶段。核心原则：**不知道原因之前不要修复**。

### 阶段一: 根因调查

这是最重要的阶段。必须完成后才能进入下一阶段。

**步骤**:

1. **仔细读错误信息** — 完整读，包括 stack trace。不要只看最后一行。
2. **一致复现** — 确保能稳定触发问题。如果随机出现，先找到稳定复现路径。
3. **检查最近改动** — `git diff` 看看最近改了什么。问题通常出在最近改动的代码里。
4. **追踪数据流** — 从输入到出错点，一步步跟踪数据怎么流过系统。
5. **诊断装置** — 在关键点添加日志/断点，缩小问题范围。

**常见陷阱**:
- 只看表面症状而非根因
- "上次也是这样"的经验偏见
- 在不理解问题的情况下乱改代码

### 阶段二: 假设形成

基于根因调查的证据，形成可能原因的假设列表：

```
假设 1 (高可能性): 数据库连接池耗尽导致超时
  证据: 错误日志显示 "connection timeout"，监控显示连接数接近上限
  
假设 2 (中可能性): 查询未使用索引导致慢查询
  证据: explain 显示全表扫描

假设 3 (低可能性): 网络问题
  证据: 无直接证据，但不能排除
```

### 阶段三: 验证

为每个假设设计**最小实验**来证明或反驳：

```
假设 1 验证方案: 增大连接池到 50，观察是否还超时
假设 2 验证方案: 添加索引，对比查询时间
假设 3 验证方案: ping 数据库服务器，检查延迟
```

从最高可能性的假设开始验证。一个假设被证实就可以进入修复阶段。

### 阶段四: 修复

确认根因后才能修复。修复时：

1. **写回归测试** — 先写一个复现 bug 的测试（RED）
2. **最小修复** — 只修复根因，不顺手改其他东西
3. **验证修复** — 运行回归测试（GREEN）+ 全部测试
4. **理解为什么** — 如果修复后问题消失但你不理解为什么，继续调查。偶然修复会留下隐患。

### 条件等待 vs 超时

当代码需要等待异步操作时，使用条件等待而非固定超时：

```typescript
// 差 — 固定超时
await sleep(5000);
expect(result).toBeDefined();

// 好 — 条件等待
await waitFor(() => result !== undefined, { timeout: 5000, interval: 100 });
expect(result).toBeDefined();
```

## 内联执行模式

无子agent支持时（Cursor、Copilot 等），按依赖顺序逐个执行任务：

1. 从 tasks.md 中找到所有无依赖（READY）任务
2. 选一个开始执行（遵循 TDD 流程）
3. 完成后标记 DONE
4. 检查是否有新任务变为 READY
5. 重复直到所有任务完成

内联模式下，自我审查更加重要——没有独立子agent来发现问题，需要在每个任务完成后认真自审。

## Git 提交规范

每完成一个 task 提交一次。提交信息格式：

```
<type>(<scope>): <简短描述>

<详细说明（可选）>
```

类型：
- `feat`: 新功能
- `fix`: bug 修复
- `refactor`: 重构（不改变行为）
- `test`: 测试相关
- `docs`: 文档更新

示例：
```
feat(auth): add JWT token refresh endpoint

Implements automatic token refresh when access token expires.
Refresh tokens have 7-day expiry with sliding window.
```
