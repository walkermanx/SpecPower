# 反理性化与最佳实践心态

在使用 SpecPower 时，保持正确的心态和警惕常见的反模式至关重要。本文档帮助你识别和克服那些可能破坏工作流效果的思维陷阱。

---

## 反理性化 Red Flags

当你发现自己在想这些念头时，停下来，按"现实"列的建议执行：

| 念头 | 现实 |
|------|------|
| "这太简单了，不需要提案" | 30秒写一段话提案不会拖慢你，但跳过可能导致方向偏差 |
| "我已经知道怎么做了" | 知道怎么做 ≠ 知道做什么。提案确认范围，设计确认方案 |
| "先写代码再补测试" | 先写测试。这是铁律，不是建议 |
| "这个测试太麻烦了" | 如果难以测试，说明设计有问题。先改设计 |
| "我先跳过审查节省时间" | 审查发现的问题修复成本是后期的 1/10 |
| "这个bug原因很明显" | 先复现，再追踪，最后修复。"明显"的原因经常是错的 |
| "自审没必要，我刚写的" | 正因为刚写的才需要自审——新鲜代码最容易有盲点 |
| "模式太严格了" | 随时可以降级。但先想想为什么当前模式被推荐 |
| "这次先不归档" | 归档只需要移动目录。不归档 = 三个月后没人知道为什么这样改 |

---

## 为什么这些念头危险

### 跳过提案的代价

**表面**: 节省 30 秒
**实际**: 可能浪费数小时在错误的方向上

提案不是官僚主义，而是思维的外部化。写下来的过程强迫你明确：
- 为什么要做这个变更？
- 范围边界在哪里？
- 成功的标准是什么？

### 先写代码后补测试的陷阱

**表面**: 快速看到结果
**实际**: 难以维护的代码 + 脆弱的测试

TDD 不是"写两遍代码"，而是：
1. 测试驱动设计 — 可测试的代码通常是好设计
2. 快速反馈 — 立即知道代码是否工作
3. 信心保障 — 重构时不害怕破坏功能

### 跳过审查的错觉

**表面**: 节省审查时间
**实际**: 后期修复成本 10 倍

审查在早期发现的问题：
- 修复成本低 — 代码还在你脑子里
- 影响范围小 — 还没有下游依赖
- 心理负担轻 — 不用面对"已上线的 bug"

## 培养正确的心态

### 1. 流程是工具，不是枷锁

SpecPower 的三档模式存在的意义就是灵活适配。如果你觉得"太严格了"，问自己：

- 是否应该降级到更轻量的模式？
- 还是这个任务的复杂度确实需要当前模式？

**关键**: 模式的选择是为了匹配任务，不是为了展示纪律。

### 2. "快"的两种含义

**假快**: 跳过步骤，短期内看起来快
**真快**: 不返工、不救火、不背债的可持续速度

在 SpecPower 中，"快"意味着：
- 第一次就做对
- 不留隐患
- 可以安心睡觉

### 3. 质量门控是保护，不是障碍

每个质量门控（TDD、审查、验证）的设计目的是：
- **及早发现问题** — 越早发现，修复成本越低
- **防止错误扩散** — 不让一个小问题变成系统性灾难
- **保护团队时间** — 不让"这个简单的修改"变成"全员救火"

## 常见误区与纠正

### 误区 1: "这个变更太小，不值得走流程"

**纠正**: Flow 模式就是为小变更设计的

```
propose ──► execute ──► verify
```

三个步骤，可能只需要 5 分钟。但这 5 分钟确保了：
- 你知道为什么要做（propose）
- 代码有测试覆盖（execute with TDD）
- 确实解决了问题（verify）

### 误区 2: "审查太慢，我自己有把握"

**纠正**: 自我审查也是审查

如果没有子 agent 支持，用清单驱动的自审。30 秒过一遍清单，能捕获 80% 的常见问题：
- TODO/FIXME 遗留
- 调试代码遗留
- 边界情况未测试
- 安全漏洞

### 误区 3: "我熟悉这个代码，不需要测试"

**纠正**: 熟悉度 ≠ 正确性

恰恰相反，熟悉的代码更需要测试：
- **防止认知偏差** — 你"知道"它能工作 ≠ 它真的能工作
- **保护未来的自己** — 三个月后你不会记得所有细节
- **保护团队** — 其他人可能修改这段代码

## 如何内化最佳实践

### 1. 从小步开始

不要一次性采用所有规则。选一个最影响你的反模式，专注改变一周：

**第一周**: 只关注 TDD — 强制自己先写测试
**第二周**: 加上自审清单 — 每次提交前过一遍
**第三周**: 开始写提案 — 哪怕只是一段话

### 2. 记录"我对了"的时刻

当某个步骤帮你避免了问题时，记录下来：

> "今天的自审发现我忘了清理测试数据，差点造成测试污染"
> 
> "提案阶段和同事讨论后，意识到我最初的方案有致命缺陷"

这些记录会强化正确行为的价值。

### 3. 原谅自己的失误

每个人都会偶尔跳过步骤、走捷径。重要的是：
1. 意识到自己跳过了什么
2. 理解这次跳过的风险
3. 下次遇到类似情况时做更好的选择

## 团队协作中的心态

### 代码审查时

**作为审查者**:
- 假设代码作者是有能力的人
- 先理解为什么这样写，再评价
- 明确区分 Critical/Important/Suggestion

**作为被审查者**:
- 不要把审查意见当作个人攻击
- 技术评估每个意见，不表演性同意
- 如果审查意见错了，礼貌地说明为什么

### 工作流选择时

**不要把模式当作地位象征**:
- Strict 不代表"更专业"，只代表"这个任务需要更多规划"
- Flow 不代表"草率"，只代表"这个任务足够明确和简单"

**目标对齐**:
团队应该就"什么样的任务用什么模式"达成共识，而不是每次都辩论。

## 验证纪律：证据先于声明

验证不是某个阶段的活动，而是**贯穿全流程的纪律**。任何声称完成的时刻——无论是一个任务、一次修复、还是整个变更——都必须有新鲜的验证证据支撑。

### 铁律

```
没有新鲜验证证据的完成声明 = 谎言
```

如果你没有在**这次操作中**运行验证命令，你不能声称它通过了。

### 验证门函数

```
在声称任何状态或表达满意之前：

1. 确认: 什么命令能证明这个声明？
2. 运行: 执行完整的命令（新鲜的、完整的）
3. 阅读: 完整输出、检查退出码、计数失败
4. 核实: 输出是否确认了你的声明？
   - 否 → 陈述实际状态及证据
   - 是 → 陈述声明并附上证据
5. 然后才能: 发表声明

跳过任何一步 = 没有验证
```

### 反合理化

| 借口 | 现实 |
|------|------|
| "应该没问题了" | 运行验证命令 |
| "我很有信心" | 信心 ≠ 证据 |
| "就这一次跳过" | 没有例外 |
| "Lint 通过了" | Lint ≠ 编译 ≠ 测试通过 |
| "子agent说成功了" | 独立验证，不信任报告 |
| "太累了不想跑了" | 疲劳不是借口 |
| "部分检查够了" | 部分什么也证明不了 |
| "刚才运行过了" | "刚才" ≠ "现在"，改过代码就要重新运行 |
| "我手动测试过了" | 手动不可重复、不可追溯 |
| "这个改动太小了" | 小改动也能引入大 bug |

### 什么时候应用

**永远在以下时刻之前:**
- 声称任何成功/完成
- 表达满意（"完成了！"、"搞定！"）
- 提交代码
- 创建 PR
- 标记任务完成
- 移动到下一个任务

---

## 总结

SpecPower 的价值不在于规则本身，而在于规则背后的**思维模式**：

1. **提前思考**（提案、设计）胜过事后救火
2. **小步验证**（TDD）胜过大步返工
3. **证据先行**（验证纪律）胜过"我认为没问题"
4. **多层保障**（审查）胜过一次通过的幻想
5. **完整记录**（归档）胜过口口相传

当你内化了这些思维模式，流程就不再是负担，而是自然而然的工作方式。
